# Driftline: Project Brief

A cozy fishing game in the browser, made for the director and their friends. It installs as an app on phones and PCs, plays offline, and updates itself. It's a side project, separate from OutPace.

**Sessions start in this folder (`C:\Users\sizze\Driftline`), never in OutPace's** (director, 2026-11-19). Driftline has its own memory; memory only points here.

## Routines (skills in `.claude/skills/`, each loads when its job comes up)
- **quick-path:** a small change (text, a number, one page, one water's art): edit, build, gate, the one relevant check, notes line, publish. The default for small changes; testing is light (director, 2026-11-21).
- **full-batch:** the round checklist, once per batch before publishing and always before anything goes live, and the end-of-project clean-up.
- **publish-test:** publishing the test builds, tester notes, version numbers, the stamp check.
- **live-and-hotfix:** anything that changes the live game.
- **new-page:** a new page, tab, chip, section, currency or device setting.
- **new-water:** a new or reworked water, with the art decisions in force.
- **testing:** the local server, sizes, hooks, the one-command sweep and baseline, saves, what the hidden pane cannot do.

## How we work (the director's standing rules)
1. **Fix every problem you find, in the same round, without asking** ("any. time. problem? FIX IT"). Ask only when the look or feel would change, and then still finish everything else first.
2. **Look for redundancy before cost:** work done twice, every frame when it could be cached or event-driven, or for something not on screen. Then measure.
3. **Decide where a fix belongs before writing it:** same picture and behaviour with less work → shared code (`src/cd_efficiency.js` or the owning core file), every platform gets it. Changes look, feel or a trade-off → that platform's files only (see Platform rules).
4. **Everything requested in one round ships together** as one update with one notes entry.
5. **Going live (director, standing permission 2026-11-20):** Claude may publish test builds and ship **live hotfixes for bugs** on its own, after the checks pass (check copy first, then a commit on the `live` branch, as in the live-and-hotfix skill), and reports each one. **Never on its own:** anything that changes look or feel (prepared on the test builds, with pictures, left for the director's green light), balance numbers (suggested, the director and Cam decide), and the 0.4.9 release itself (after the director has tested it on every platform). Before changing any system, tag a rollback point (`rollback/before-<what>`) so it can be reverted.
5b. **Changes the director or Cam asked for are built as asked** on the test builds; where the request leaves a number, timing or look open, Claude builds a first version and flags it (**Feel call**) instead of tuning it alone.
5c. **Rules become tools (director, 2026-11-20):** whenever a written rule can be checked by a tool (a build refusal, a QA test, `__contentQC`-style check), build the tool, prove it by planting the mistake once, then shorten the written rule to one line pointing at the tool.
6. **Every message about a change starts with where it is:** **Test builds only** / **Live (which platforms)** / **Not published**, plus the stamp; a small table when a batch is mixed.
7. **Design first:** sketch the whole layout and its purpose before moving UI; never patch piece by piece.
8. **Quality bar:** no errors, no "approximately right". Test every combination that applies; self-critique ("what would the director notice first?") before showing anything.
8b. **Look at it yourself first (director, 2026-11-22):** every change to how something looks gets Claude's own pictures before the director sees it: every water it touches, resting and fishing, phone and PC (`__shot(name, water, rest)` in a `?test` page posts to the local server's `/shot/<name>`, saved in `tools/shots/`; contact sheets per set). Look changes then go on a picture page (artifact) the director comments on from the phone, before the test builds. Screens follow the Driftline design system; **every design-related change also updates the Driftline Design System** (director, 2026-11-22: "fully update it with all of our data, feedback and memory"): its rules, cards and right/wrong pictures, the director's and Cam's feedback, and what was learned, in the same round; `/simplify` for the end-of-batch clean-up pass and one code review (`/code-review`) per batch before publishing.
8c. **Keep the record live (director, 2026-11-23):** as you work, write every change and every bug you catch into CLAUDE.md ("Where we left off", the batch's line) and, for anything about looks, controls or art, into the Driftline Design System, in the same step; bugs also get their row in docs/qc_incidents.csv.
9. **Smooth over frugal where it is cheap:** animations and effects run at full frame rate when the measured cost is small; phones throttle only what measurements show is costly.
10. **Never take computer-use screenshots of the Driftline app** (it hides and minimizes the window); ask the director for a pasted screenshot.

## Platform rules (director, 2026-11-18: "create ground rules going forward so we'll never have the problem")
`build.ps1` enforces 1–3 and refuses to build when one is broken.
1. **Three builds, one game:** `pc.html`, `android.html`, `ios.html` behind a router `index.html`; one shared core (game, rules, drawing, save) and one save.
2. **Platform code lives only in its folder:** `src/pc/` (PC), `src/mobile/` (Android + iPhone), `src/android/`, `src/ios/`. Add files to `$layers` in build.ps1, or place a `//@layer <platform> <file>` marker in a shared file. Shared files may not gain platform mentions (counted against `$platBaseline`, which only goes down).
3. **Every build holds exactly its own platform files.**
4. **Shared rules and data go in the core** (rewards, balance, items, saving), written once; each platform then gets its own screens for it.
5. **Old platform code in a shared file is moved to its platform folder before it is changed** (marker in its place, baseline lowered).
6. **A platform-specific change touches only that platform**, scoped to its body class (`pch-on` / `pc-fhd` PC, `phone-land` phone sideways, `phone-app` narrow windows), and is tested on that build. Shared core changes and shared efficiency fixes are tested on all three builds. **Android and iPhone share one phone layer (director, 2026-11-20):** in Chrome both builds are the same code and engine, so phone checks run once (the full-batch skill); what differs between the phones (Safari drawing, Android full screen and frame rate) only shows on the real phones, which the director (iPhone) and Cam (Pixel) check. A bug report names the phone it was seen on; the fix goes in the shared phone code unless the cause is that phone alone (12 of the first 130 bugs were).
7. **Screens follow `docs/PLATFORM_DESIGN.md`.** Anything it doesn't cover is added there first (asking the director when it is a real design choice).
8. **Fixed device rules (director's decisions):**
   - Phones are **landscape-only** (a "turn your phone" screen while upright; Android also locks while full screen). The narrow `phone-app` layout only appears in split-screen / small windows.
   - Phones are **always full screen**, no Settings option (iPhone via the home-screen app; Android via `manifest-android.webmanifest` + re-entry on a finished tap).
   - **Frame rate:** Android draws 60 fps (also on 120 Hz screens), iPhone its natural rate; no frame-rate choice on either.
   - **Settings are per device** (`src/mobile/settings08.js`, `DEV_KEYS`); progress and gameplay choices travel with the save. Show only settings that work on that device.
   - **Tablets** are the phone layouts scaled up (`src/mobile/tablet08.js`); no separate tablet layout without the director.
   - **PC:** nothing sits on top of the fishing scene; the header is one clean row. The director plays full screen at 1920×1080.

## How it's built
- `build.ps1` concatenates `src/shell_top.html` + the shared `$core` list + the platform's `$layers` + `e_ui.js` + `shell_bottom.html` into one IIFE per platform (`site/pc.html`, `android.html`, `ios.html`, router `index.html`); `-Preview` writes `site/next/` and `testapps/`, adds the test hooks (`bn_qa04.js`) and `DL_PREVIEW`.
- **Saves:** `localStorage` `driftline-save-v1` (preview `driftline-save-next`); loading is one function, `migrate()`, and saving is one function, `save()`, both in `c_logic.js` (F6, 2026-11-26): a new save rule is a new step inside them, never a wrapper in a later file. Data that saves are checked against lives in `b_data.js` (loads before the logic). `fresh()` and the core part of `migrate()` (above its `coreOnly` line, the only part that runs at the first read) use only plain values or `b_data` constants; the steps below it call their owner files. Phones add their own step through `deviceLoad` / `deviceSave` (`mobile/settings08.js`). Any change here is proven with `tools/saveprobe.ps1` (testing skill).
- **Panel buttons:** `data-act`; `e_ui.js` falls through `extraAct` → `extraAct2` … `extraAct7`; each returns `undefined`, `'render'` or `'skip'`.
- **Bonuses:** `bonus(k)` sums buffs, aquarium, pets and rod, with caps; the favourite pet gives its full bonus, the companion `compShare()` (50% + 2% per bond level).
- **Moving progress:** save codes `DL1:` + deflate + base64; links `#load=`; 6-digit transfer through ntfy.sh topic `driftline-move-<code>` (newest file of the last 3 hours, then `<code>-ok`); the QR encodes `#pair=<code>`.
- **Hosting:** GitHub Pages (`sizzentra/driftline`, branch `gh-pages`: the live files at its top, the PC test build in `next/`; the phone test apps and the hotfix check copy are a second Pages project, `sizzentra/driftline-test`, = `testapps/`). The live files come from the `live` branch (`tools/push_live.ps1`), `next/` from `main`'s `site/next/`; `main`'s `site/` also keeps a copy of the live files, which must equal `live` (`tools/push_folder.ps1` refuses otherwise). The shared checkout stays on `main`; `live` is worked on in its own folder (`git worktree add ..\Driftline-live live`). The service worker fetches network-first; the update banner compares the page stamp with `version.txt` (PC) / `version-phone.txt` (phones).
- **Feature switches (2026-11-26):** `FEATURE` in `b_data.js`: one line turns a larger feature off without deleting it; its save data stays, unread. Each has one guard at its owner, and the `__qa` tests follow the switch. `controller:false` (k_controls.js); on: `fightFeel` (Cam's fight, c2_fightfeel.js `fishNew`; off = the earlier fight), `inspect` (cz_inspect.js), `boardwalkExtras` (Gamble, Treasure chests, coin jackpots; ci_boardwalk.js), `installWelcome` (cy_install.js). A new switch is proven both ways: on with the baseline and the sweep, off with `tools/sweep_all.ps1 -Only gate,boot,qa,content`.
- **Publishing a folder (test builds):** `tools/push_folder.ps1` puts the committed `site/` or `testapps/` on its Pages branch as one commit and checks the published files are identical (never `git subtree push`: it re-read the whole history, minutes per folder).
- **Windows app:** `desktop/Driftline.cs` (WebView2 wrapper of the live site); `desktop/build_desktop.ps1` builds `site/download/Driftline-Setup.zip` (rebuild only when Driftline.cs changes).

## Code rules (details and history in docs/LESSONS.md)
- **Redundancy only goes down (the build refuses, 2026-11-20):** no unused functions, and no new wrap layers (`name = function`), force-hide rules (`display:none!important`), polling timers (`setInterval`) or watchers (`MutationObserver`): edit the owner, build only what is shown, update on change. The build saves lower numbers by itself.
- **No silent catch (the build refuses, 2026-11-27):** a catch that carries on calls `oops('file:what', e)` (`a3_plat.js`: the one reporter; a short list in memory, shown in Stats, Tester tools and read by the checks through `__errs`); an empty catch or `.catch(()=>{})` stops the build. Only where reporting would be noise by design: `/* quiet: reason */` in the body, counted with the redundancy numbers (may only go down).
- **No garbled characters (the build refuses, 2026-11-26):** a script that rewrites a UTF-8 file in the wrong encoding garbles every special character. `tools/mojibake.ps1 <file>` finds them, `-Fix` repairs. Docs and notes are edited with the editor; anything with a backslash or a special character never goes through `sed` or a here-document (the shell ate backslashes four times on 2026-11-26).
- One-line style files: a `//` comment mid-line eats the rest of the line; use `/* */`.
- **PC CSS sizes use `calc(N*var(--uvh,1vh))`, never raw `vh`/`dvh`** (the PC interface zoom multiplies viewport units).
- **New save fields go in `ck_bootfix.js` keys:** the save is loaded at start-up before later files exist, so a field set by a later step of `migrate()` reaches the start-up save only through those keys (or through its owner file running the step on `S` when it loads).
- **Code that runs while the page is loading can't use anything defined further down:** a timer's first run goes after loading (`setTimeout(tick,0)`), never an immediate call (#130).
- `e_ui.js` comes after the platform layers: never read its `let/const` at load from a platform file; wrap functions only.
- Check whether a name is `const` or `function` before wrapping it (wrapping a const kills the page).
- **Dead-code ground rule (director, kept):** never replace a whole function from a later file and leave the original behind: edit the original, or delete it and make the replacement the one `function name(...)`. The build refuses a full replacement that doesn't keep the old one (`const _x = name`); a platform file overriding a shared default is allowed. Test hooks call functions through a wrapper, never by value.
- Older phone CSS rules often carry extra ids/classes and silently win; measure the rendered result, and list the matching rules when a new one loses.
- No regex look-behind `(?<=` in phone code (older iPhones fail to parse the whole page).
- Shell edits: `sed`/`perl` mangle `$`, backslashes and `\b`, and multi-line patterns fail on CRLF; use the Edit tool for those, and `grep -rlP "\x08" src` after shell edits. A line-based insert or delete lands by line number, not by meaning (one went inside a multi-line function, one removed a closing brace): print the lines around it right after.
- `git checkout -- site/next` serves an old build locally until you rebuild.
- **Safari sizes things differently from Chrome:** never let a layout hang on one mechanism (a rail sized only by being stretched collapsed on iPhone); when a phone screenshot shows something Chrome can't reproduce, fix it robustly, add a check that forces the failing condition, and say it is not verified on Safari.
- **No `!important` on `display`** for anything that can sit in a tabbed page (page tabs hide with an inline `display:none`); if unavoidable, add `:not([style*="display: none"])`.
- **One owner per element:** one block creates, places and hides it; find page parts by their title or a data attribute, never by a styling class or an old class a page engine may drop.
- **Compare what the player sees:** tab names from the shown text (`tabShownName`), never from `data-sect` ("Dock" shows as "Your boat").
- **Scene state (night, weather, the angler's pose) is put back by the code that set it;** a save-and-restore copied into several callers means the source is wrong: fix the source, delete the copies.
- **A layout change runs `__spec` at every size it touches;** when the new size is right, MB_FRAME and the PLATFORM_DESIGN table change in the same commit.
- **When a feature moves, its old builder and hiding rules are deleted in the same change** (an old on-water Bait button was still built every second and hidden by CSS).

## Ground rules for the game (director)
- **Fishing stays the core.** Everything else supports it.
- **Cozy and homey,** light humour everywhere but never the focus.
- **Try before you buy:** every purchase has a preview.
- **Don't over-buff,** but make every choice meaningful.
- **No easy way to delete progress:** reset needs a typed DELETE and makes a backup first.
- **It should feel like a real app,** with a clean look on phone and PC.
- **A 2D side-view game (director, 2026-11-21):** everything is drawn as seen from the side (a canopy is a roof profile, a boat a hull outline), never as a front or top view squeezed in.
- **Art direction "Glow Diorama":** rich glow lighting, crisp layered depth, rim light, bloom on lights, everything gently alive. Nothing floats or looks pasted on: attachments are placed from the real outline (`f3TopY`, `f3TopAt`, `horseCX`), never guessed offsets.
