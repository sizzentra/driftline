# Driftline: testing reference

- **Local server:** `tools/serve_local.ps1` serves `site/` at `http://localhost:8766/` (already running in long sessions; don't start it twice). Builds: `/next/pc.html`, `/next/android.html?test`, `/next/ios.html?test&iphone`.
- **One-command checks (Foundation F1, 2026-11-26; for proving, the pane stays for looking):** `tools/sweep_all.ps1` runs the whole sweep in an invisible browser (Edge, nothing installed) on the three test saves kept in git (`tools/saves/new.json`, `mid.json`, `heavy.json`, made by `__mkSave`; no gift pets), about 14 minutes a save, reports in `tools/shots/sweep_<save>.json`, deaf to game controllers; `-Saves new -Only gate,qa` narrows it. `tools/baseline.ps1 -Check` compares about 420 fingerprints per save (every water at dawn, day, dusk and night, every menu page and page tab, on PC, iPhone and Android builds, `?test&frozen`, drawn without the graphics card) with the agreed set in `tools/baseline/`; `-Make` stores a new agreed set (only from a build whose look is approved). A change that must not alter anything on screen is proven by `-Check` passing; a look change is followed by `-Make`. The sweep page also takes `?save=<name>` in the pane. How they were made steady: LESSONS, "Foundation F1".
- **Sizes:** phones sideways 956×440 (the director's iPhone 16 Pro Max), 874×402, 667×375, 915×412 / 780×360 (Android); split-screen 440×460 and 375×812; PC full screen 1920×1080, plus 1440×900 and 800 wide.
- **Tester tools › Time and weather (2026-11-22):** preview builds move the game clock (`window.__tOff`, kept in localStorage `dl-test-toff`; `?test`, `?sweep` and `?frozen` pages ignore it), so the director can see any time of day or weather at once.
- **Frozen start (`?frozen`, preview builds, 2026-11-22):** the same random numbers, a clock that only moves when the game asks for the time, and no frame loop, so two different builds start in exactly the same state; draw a frame by hand and compare (how the water-files split was proven: 20 waters, day and night, pixel-identical).
- **Hooks (`?test` only):** `__qa`, `__shot` (pictures, rule 8b), `__cropShot`, `__homeSheet` (every water's home, fishing and resting, on one sheet), `__timeSheet` (a moving thing through its whole loop), `__feelSim` (fight landing times), `__contentQC`, `__mapQC`, `__pathsAll`, `__layoutQC`, `__searchQC`, `__questsQC`, `__spec`, `__safeSim`, `__ui.open/close`, `__setPhase`, `__setWeather`, `__findWx`, `__drawCost`, `__prof`, `__mobperf`, `__fishParts`, `__fishSheet`, `__crop`. Game globals are not reachable from the console (one closure); drive the game through `data-act` / `data-tab` buttons or hooks.
- **The sweep page** (`tools/sweep.html`, copied to `site/next/` by the preview build; testers open it from Stats › Tester tools › Run every check, which runs it in Safari / Chrome on the real phone, and send its Copy report text; the link passes `?dev=ios`/`?dev=android`, so a phone runs only its own build at its own screen size, and a run resumes after the phone reloads the page, #150) opens a fresh copy of the game for every check, so back-to-back runs cannot collide and no check starts with a menu open; it runs fine in the hidden pane (preview pages opened with `?sweep` get a frame timer and record every start-up error, from build.ps1). Poll `window.__R.state` or wait for `tools/shots/sweep.json` to change.
- **The browser pane is usually hidden:** no animation frames, frozen CSS transitions, no Resize/Intersection observers, stale screenshots, and calls time out after 45 s. Start long checks in an async block that writes to `window.__R`, return at once, poll in later calls that wait at most ~30 s each (the tool gives up at 45 s). For a running frame loop, test a copy of the build with requestAnimationFrame shimmed to setTimeout (8 ms = 120 Hz, 16 ms = 60 Hz) in `site/next/_ab/` (delete afterwards).
- **Frame-rate problems are measured on real frames (director, 2026-11-21):** ask the director to show the browser pane (Ctrl+Shift+B) and measure there, on this PC's graphics card, or read the director's frame counter (Settings › Display › Show frame rate). The hidden pane showed Willow Pond as smooth while the director saw 300 ms freezes at dawn and dusk.
- **Measuring:** `setTimeout(0)` adds ~4 ms per step; never run two timing loops at once; freeze `Date.now` when comparing scenery; force a real scenery rebuild with the Graphics test 1x toggle twice; the desktop GPU hides raster cost, so count work, not just milliseconds.
- **Split-screen sizes in test mode:** the turn screen follows the window's shape there (real phones use how the phone is held), so hide `#dl-turn` before `__spec` at 440×460 / 375×812 / 360×780.
- **Saves for testing:** edit saves from `/version.txt` (a non-game page), because the game saves on unload. Preview builds use `driftline-save-next`. **The browser pane's storage is wiped when the Claude app reloads** (2026-11-22): the test save is kept in `tools/shots/testsave.json` (POST `/report/testsave` from a game page after `save()`); restore it from `/version.txt` by copying it beside the build, writing its **`save` field** (the file is `{save, at}`; writing the whole file gives the game an empty save, 2026-11-22) to `driftline-save-next`, and deleting the copy.
- **Test apps:** phones: "DL Test Android" / "DL Test iPhone" from https://sizzentra.github.io/driftline-test/ (`publish_testapps.ps1`). PC: "Driftline Test" desktop app (`desktop/DriftlineTest.cs`, loads `/driftline/next/` full screen; F5 reload). Tester tools in Stats (preview only, `DL_PREVIEW`) unlock everything and include the Graphics test; never in a release build.
- **A phone start-up problem Chrome can't reproduce:** get the error from the phone first (`testapps/checkup.html`, a read-only page published with the test apps that shows what the phone stored and the start-up errors) before changing anything. A check that runs a phone build as a PC (Windows user agent, fresh save, no update path) proves nothing about phones.
- **Game controllers:** switched off in the game since 2026-11-26 (`FEATURE.controller`), and the sweep and baseline pages make the game under test deaf to them, so a controller in use on this PC no longer reaches the fight tests. If the switch goes back on: a held trigger reels, and `__qa` run by hand in the pane (outside the sweep page) needs the controller idle.
- **Hotfix check copy:** https://sizzentra.github.io/driftline-test/hotfix/ (same origin as live, so it plays on the real save; safe only because it is the live code plus the fix).
- **Never take computer-use screenshots of the Driftline app** (it hides and minimizes the window); ask the director for a pasted screenshot.
